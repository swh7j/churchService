# 트러블슈팅 기록

운영하면서 겪은 문제와 고친 과정을 적어 둡니다. README 에는 이 중 몇 개만 요약했습니다.

## 찬송가 .ppt 를 그림으로 바꾸니 노을 배경이 빠짐

찬송가 PPT 를 열어 보니 배경 사진은 슬라이드 마스터에 있었고, 악보와 가사는 그 위에 얹은 투명 PNG 였습니다.
슬라이드에서 가장 큰 그림만 꺼내는 방식이라 배경이 통째로 빠졌습니다.

Apache POI(HSLF)로 슬라이드마다 배경 채우기, 마스터의 그림, 슬라이드의 그림 순서로 한 장에 합성하게 바꿨습니다.
묶음 도형은 좌표를 변환해서 그리고, 서버에 글꼴이 없어도 되게 글자는 그리지 않습니다.
빨간 배경에 가운데 파란 투명 그림이 있는 .ppt 를 테스트에서 직접 만들어 구석과 가운데 색을 검사합니다(`PptImagesTest`).

## 찬송가 31장만 "그림 없음"으로 실패

파워포인트에서는 멀쩡히 열리는데 POI 로는 그림을 하나도 못 찾았습니다.
파일 안에 지워진 빈 그림 칸(BSE)이 남아 있어서 POI 가 그림을 한 칸씩 밀려 연결하고 있었습니다.

라이브러리가 못 찾으면 그림 고유값(UID)으로 직접 찾아 붙이게 했습니다. 645개 파일을 전부 돌려 보니 걸리는 건 31개뿐이었습니다.
고치는 김에 두 가지를 더 손봤습니다. 이름은 .ppt 인데 속은 .pptx 인 파일이 있어서, 확장자 대신 파일 앞부분을 보고 형식을 판단합니다.
가사가 그림이 아니라 글자로 된 화면은 빠질 수 있어서, 올릴 때 "확인 필요" 경고를 띄웁니다.

## 교회마다 찬송가를 따로 저장하다가 디스크가 9일 뒤 찰 뻔함

처음엔 찬송가를 교회 DB 에 넣었습니다. 두 교회가 같은 찬송가(각 1.2GB)를 따로 갖고 있었고,
매일 DB 전체를 백업해서 30개를 보관하니 백업 한 번이 2.5GB 였습니다. 남은 20GB 가 9일쯤이면 찰 상황이었습니다.

찬송가는 어느 교회나 같으니 서버에 한 벌만 두는 공용 보관함으로 옮겼습니다(DB 밖 파일 + platform.db 목록).
두 교회 자료를 공용 목록과 하나씩 대조해 빠진 곡이 없는 걸 확인한 뒤 비우고 `VACUUM` 했습니다.
교회 DB 는 1.2GB 에서 4.9MB 로 줄었고 매일 백업도 몇 MB 수준이 됐습니다.

## 사진 때문에 매일 백업이 30배로 커질 문제

사진을 DB(BLOB)에 넣으면 매일 백업을 30개 남기니까 사진 용량도 30배로 쌓입니다.
그래서 사진은 `data/photos/{교회}` 에 파일로 두고, 백업할 때 새 사진만 `backups/_photos` 로 복사합니다.
지운 사진의 백업본은 30일 보관 후 정리합니다. 사진을 올려도 DB 백업은 수백 KB 로 유지됩니다.

## 앨범 목록 쿼리에서 `no such column: a.cover_id`

대표 사진을 고르려고 스칼라 서브쿼리의 `ORDER BY` 에서 바깥 테이블 칸을 참조했더니 SQLite 가 해석하지 못했습니다.
`LEFT JOIN album_photos c ON c.id = COALESCE((지정한 대표), (첫 사진))` 구조로 바꿨고, 실제 DB 에 쿼리를 먼저 돌려 본 뒤 반영했습니다.

## 결산보고서가 A4 3장으로 인쇄됨

화면에서는 수입과 지출 표가 나란히 있지만 A4 폭에서는 위아래로 쌓여 100줄 가까이 됐습니다.
결산 화면이 열려 있을 때만 `@page`(A4, 여백 8mm)와 인쇄용 촘촘한 서식을 적용해서 인쇄 때도 좌우로 놓이게 했습니다.

## 로그인 잠금이 오히려 공격 수단이 될 수 있음

처음엔 "아이디별 5회 실패하면 잠금"이었는데, 이러면 누구나 관리자 아이디로 일부러 틀려서 관리자를 계속 잠가 둘 수 있습니다.
기준을 아이디+IP 로 바꾸고, 한 IP 가 여러 아이디를 시도하는 경우와 여러 IP 가 한 아이디를 노리는 경우를 따로 제한했습니다(`LoginGuardTest`).

## 메모리 1GB 서버에서 큰 파일 다루기

앨범 전체 내려받기(최대 300장)를 메모리에서 zip 으로 모으면 힙(384MB)을 넘길 수 있어서 응답 스트림에 바로 쓰게 했습니다.
사진은 올리기 전에 브라우저에서 긴 쪽 1600px 로 줄입니다. 휴대폰 원본 3~5MB 가 0.3MB 정도가 됩니다.

## "PPT 에서 찬송가가 반복되고 겹쳐요" (아이폰에서만)

PC 의 PowerPoint 로 화면을 하나씩 그림으로 뽑아 보니 파일은 정상이었습니다. 그런데 휴대폰 화면에는 그 파일에 없는 곡이 섞여 있었습니다.
같은 주보로 여러 번 만들면 파일 이름이 매번 같은데, 아이폰 미리보기가 같은 이름의 예전 파일 화면을 다시 쓰고 있었습니다.
파일 이름에 만든 시각을 붙여 해결했습니다.

살펴보다가 진짜 문제도 몇 개 찾아서 같이 고쳤습니다. 주보에서 찬송 번호를 못 찾은 칸은 빨갛게 표시하고 만들기 전에 한 번 묻고,
교회소식 글상자가 배경 그림과 겹치지 않게 폭과 한 화면 글자 수를 줄였습니다.

## 아이폰에서 가끔 "Load failed"

서버 로그에는 그 시각에 오류도, 요청 기록도 없었습니다. 요청이 서버에 닿기 전에 끊긴 것이었습니다(앱 전환, 화면 잠금, 와이파이와 데이터 전환).
사파리는 이럴 때 영어 오류를 그대로 보여 줍니다.
조회(GET)는 1초 뒤 한 번 더 시도하고, 그래도 안 되면 한국어로 안내합니다. 저장은 두 번 저장될 수 있어서 다시 보내지 않습니다.

## CI 에서만 가끔 실패하는 백업 테스트

로컬에서는 매번 통과하는데 GitHub Actions 에서만 가끔 "방금 백업했습니다"(400)로 실패했습니다.
백업 파일 이름이 초 단위라서 같은 초에 두 번 만들면 두 번째를 거절하는데(연타 방지), CI 가 빨라서 앨범 테스트와 백업 알림 테스트가 같은 초에 백업하고 있었습니다.
지난 실패 5번의 로그를 다 열어 봤는데 원인이 전부 같았습니다. 테스트에서는 거절되면 1초 기다렸다가 다시 만들게 했습니다.
